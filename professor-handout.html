EssayScaff — Information for Instructors

A rule-based academic writing scaffold: guidance and feedback, never ghostwriting, never grading.

1. What it is

EssayScaff is a web application that guides students through planning an essay in four stages — Idea → Thesis → Outline → Reflection — followed by a Writing Lab for drafting. In Student Mode the sidebar acts as a writing-coach dashboard showing one primary action at a time (current goal, one feedback card, what's working, next step, checklist, writing snapshot, history link). Every finding is explainable in Transparency Mode.

2. The student workflow

StageStudent producesSystem checks
1. IdeaInitial idea, topic, keywordsDevelopment, focus, topic connection (PREWRITE rules)
2. ThesisOne thesis claimStructure, specificity, scope, alignment with Stage 1 (THESIS rules)
3. OutlineBody points + supporting detailsThesis alignment, support, duplicates, coverage (OUTLINE rules)
4. ReflectionReview of the full planRecurring issues, regressions, stability (REFLECT rules, scaffold levels)
Writing LabThe essay draft (introduction / body / conclusion)Live writing feedback + starter guidance per section

Students advance only through readiness gates (e.g. a thesis cannot proceed from an unready idea — enforced server-side). All revisions are stored append-only; nothing is overwritten.

3. Technical foundation

  • spaCy — sentences, tokens, lemmas, POS, dependencies (conservative normalization only)
  • Hand-written keyword ranking — frequency + POS + distribution score, fully shown
  • NLTK WordNet — lexical expansion of teacher keywords (query only)
  • scikit-learn TF-IDF + cosine — 2 documents (topic vs. student), independently re-verified
  • LanguageTool — mechanics only; grammar never blocks progress
  • Deterministic rules + readiness — no machine-learning classifiers in the loop

4. Guarantees that matter for teaching & research

  • Authorship preserved. The system asks questions and gives feedback; it generates no sentences and rewrites nothing.
  • No grades or scores. Topic connection (WEAK / MODERATE / STRONG) is labeled lexical evidence — not a grade.
  • Fully inspectable. Transparency Mode shows tokens, keyword math, TF-IDF vectors, cosine verification, every rule with evidence, and readiness conditions.
  • Traceable. All revisions, triggered rules, and timestamps persist; resolved issues remain in history.
  • Frozen for validation (VR-2). Detector code and thresholds are hash-pinned; no validation run executes unless both hashes match.

5. Honest limitations

No generative AI is used. The system works on lexical evidence only — it has no deep semantic understanding, and grammatically valid nonsense may pass some checks. Formal accuracy has not yet been established. Privacy by design: analytics record counts and timings only — never essay text or keystrokes.

EssayScaff — Technical Feedback Flow

How one student text becomes feedback: a deterministic, fully inspectable pipeline.

  1. Input. A string (student text) + optional topic/teacher keywords + stage label. Nothing else.
  2. Normalization (conservative). Unicode NFC + newline unification only — no lowercasing, no punctuation stripping, no stopword removal — so later findings point to exact character offsets.
  3. spaCy: sentences → tokens. Sentence spans, then per-token text, lemma, POS, tag, dependency, stopword flag, offsets. EssayScaff does no manual tokenizing; it reads these properties.
  4. Keyword extraction (own formula, not TF-IDF). score = freq_weight × ln(1+freq) + POS_weight + dist_weight × (sentences_with_term / total_sentences), with per-term score parts stored and displayed.
  5. WordNet expansion (teacher concepts only). NLTK lookup logged as DIRECT / LEMMA / WORDNET / NO_MATCH with synsets and rejection reasons. Never injected into the essay analysis.
  6. TF-IDF + cosine + classification (scikit-learn). Exactly 2 documents (topic vs. student). IDF(t) = ln((1+N)/(1+DF(t))) + 1; cosine is independently recomputed by hand and must MATCH within tolerance; the number is banded WEAK / MODERATE / STRONG — lexical overlap only.
  7. Generic writing rules. Pattern/heuristic detectors (THESIS_001/002, STYLE, MECHANICS, LanguageTool) each return rule id, status, severity, sentence, evidence object, offsets, reason. Grammar is advisory and can never block progress.
  8. Stage rules (pedagogy layer). PREWRITE_001–008, THESIS_001–010 (+ subject/verb/stance components, Stage-1 alignment), OUTLINE_001–011 (+ unity, progression, duplicates, coverage), REFLECT rules over stored histories (recurring issues, regressions, scaffold level).
  9. Prompt selection = priority sort + anti-repetition. Fired rules sorted by explicit priority_rank (CRITICAL 0 → LOW 3); already-shown prompts deprioritized, so feedback fades as issues resolve. Showing only the head of this list is what makes Student Mode progressive.
  10. Feedback assembly + backtrace. Each card carries the chain original text (chars X–Y) → evidence → rule (file :: function) → problem → category → reason → suggestion. Any card traces mechanically to its exact text span and rule. Suggestion strings are static per rule; only evidence slots come from the student.
  11. Readiness gate (structural, no scores). Explicit PASS/FAIL conditions per stage (e.g. development, topic concepts, focus, no critical issue); all PASS sets the gate flag, enforced server-side (linked analysis on a not-ready session returns 403).
  12. Append-only persistence. Analysis, rule outputs, prompts, readiness, and timings stored as a new revision row; history is never updated or deleted — the basis for resolved-issue tracking and VR-2 validation hashes.
In one paragraph: a deterministic pipeline — spaCy annotates the text, a transparent keyword formula and WordNet describe the concept space, scikit-learn TF-IDF/cosine measures topic overlap (hand-verified), hand-written heuristic rules fire over that evidence, a priority-ranked selector with anti-repetition picks the questions, each card carries a backtrace to its exact text span and rule function, explicit readiness conditions gate progress, and every revision persists append-only. No ML classifiers, no generative model, no scores.

EssayScaff — Architecture & Research Design

Sessions, presentation policy, analytics, validation, and system structure.

1. Cross-stage session linking

Each stage analysis creates a revision inside a session (e.g. SES-…, SES2-…). Clicking "Continue" carries the real parent session ID forward, so the chain Idea → Thesis → Outline → Reflection → Writing Lab stays linked (topic, keywords, and prior text travel with it). Protections: a stage session from a different chain is never silently reused (the client resets to the current chain's session — no rows deleted); linked calls against not-ready upstream sessions are refused server-side (403); an explicit unlinked research mode (manual session fields, direct tab access) remains available.

2. Progressive feedback policy (presentation only)

The backend always detects and stores all findings. What the student sees is filtered:

  • One primary card — head of the backend's priority-ranked list (priority_rank: CRITICAL 0 → LOW 3). Resolving it surfaces the next item on re-analysis.
  • Prompt fading / anti-repetition — already-shown prompts are deprioritized per session.
  • Dashboard — static current goal, "Why am I seeing this?" (student-friendly, no rule IDs), ≤3 proven "What's working" items (each traced to a real PASS status/classification), one next-step hint, readiness checklist (✓/○/!, no raw C-ids, max 5 rows), writing snapshot (words, sentences, revision, analytics active time, topic connection labeled not a grade), plus a Previous-feedback row into history.
  • Starter guidance in an empty Writing Lab section (fixed instructional copy — never generated sentences).

3. Analytics (counts only, privacy by design)

  • Interaction events (append-only): stage entries, analysis requests, revisions, feedback displays, Continue clicks — referencing session/analysis/revision IDs. Strict validation: essay text can never be smuggled into metadata; only APP_OPENED/SESSION_ENDED may omit a stage.
  • Time on task: client-measured active time (visible tab + recent activity; idle/hidden time excluded), stored as idempotent intervals, aggregated per stage and total.
  • Aggregates are deterministic counts over stored rows — revisions, feedback items, active time, readiness transitions. Never scores, never predictions. No keystroke content is ever logged.

4. Validation workspace — Phase 7A (how accuracy would be proven)

  • Frozen datasets (SHA-256 hash recorded at freeze) with independent human labels per sample, plus an adjudication protocol for disagreements and UNCLEAR cases.
  • Immutable runs: a run executes frozen VR-2 detectors over a frozen dataset; predictions, confusion cells, and metrics are persisted with the code/config snapshot — re-runnable and auditable.
  • VR-2 freeze gate: every run verifies the live rules/*.py hash (8ac38bf3…) and frozen-threshold config hash (401f3a4b…) against pinned values; any detector or threshold change requires a new ruleset version, never a silent edit.
  • Student traffic and formal validation data are kept separate; test/verification sessions are never treated as research data.
